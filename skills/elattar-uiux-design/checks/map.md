# Checks: which rule each one enforces

Every check exits 1 on a finding. **Nothing runs them automatically** unless
the project installed the hook and CI (`install`). Run them yourself.

`<skill>` is this skill's base directory. Entry point: `node <skill>/checks/run.mjs <mode>`.

## Modes

| Mode | Runs |
|---|---|
| `fast` | every static check: `tokens`, `rules`, `refs`, `contrast`, `motion-static`, `content`, `ux`. In a git repo: only files changed vs `HEAD` plus their importers (`--changed`, the default); `--all` for everything |
| `full` | `fast` plus every browser check: `contrast-rendered`, `layout-shift`, `rhythm`, `emphasis`, `motion`, `keyboard`, `ux-flow`, `runtime-errors`, `page-length`, `anchor-nav`, `nested-radius`, `nav-reach`, `overlap`, `truncation`, `title-scale` (needs a running app and Playwright). Routes: `--route <r>` (repeatable), else the changed pages plus `/` in a git repo, else (or `--all-routes`) every route in the config. `--only a,b` runs a subset of either mode |
| `tokens` · `rules` · `refs` · `contrast` · `motion-static` · `content` · `contrast-rendered` · `layout-shift` · `rhythm` · `emphasis` · `motion` · `keyboard` · `ux` · `ux-flow` · `runtime-errors` · `page-length` · `anchor-nav` · `nested-radius` · `nav-reach` · `overlap` · `truncation` · `title-scale` | one check only (browser checks take routes like `contrast-rendered`; `motion` takes `--component <part of a path>` instead) |
| `motion [--component <part of a path>] [--base <url>]` | drives each `motionPhases` row that has a `specimen` on the running app and samples it frame by frame; rows without a specimen, and modes it cannot measure for a row, are listed in a NOTE |
| `contrast-rendered [<route>…] [--route <r>] [--base <url>]` | what the running app paints on every route (default: `routes` in the config), light and dark; text over images is counted in a NOTE |
| `runtime-errors [<route>…] [--route <r>] [--base <url>]` | per route: console errors, uncaught exceptions and the framework's error overlay; any one is BAD with its message (see "Real apps" below) |
| `shots <route>… [--base <url>] [--out <dir>]` | not a check: PNGs at `<root>/.viewsonic-ui/shots/<route-slug>/{light,dark}-{phone,desktop}.png` (390×844 and 1440×900, full page, reduced motion) and, for a page taller than one viewport, viewport-tall slices `<route-slug>-<theme>-<device>-<n>.png` beside them (max 8 per page; review these); prints each path; exit 0 |
| `contrast --fg <token> --bg <token> [--kind text|large|ui]` | one pair, both themes: ratio, GOOD/BAD, and tokens that would pass |
| `config` | prints the discovered project configuration |
| `install` | writes the commit hook, CI workflow and config into the project (plan only without `--yes`) |

## When to run

| Moment | Command |
|---|---|
| After every meaningful edit | `node <skill>/checks/run.mjs fast` (scoped) |
| Before saying "done" | `node <skill>/checks/run.mjs full` (changed routes) |
| The complete run (CI) | `node <skill>/checks/run.mjs full --all --all-routes` |
| Unsure what was detected | `node <skill>/checks/run.mjs config` |

## Real apps: dev servers, sign-in, states

- **Dev overlay.** The Next.js dev indicator and error dialog (`nextjs-portal`, `[data-nextjs-*]`), the Vercel toolbar and the Vite and webpack overlays are not the page: every browser check skips them (one helper, `window.__isDev`, in `browser/lib.mjs`). Their errors are reported by `runtime-errors`.
- **Hydration.** Every browser check waits until the page has loaded, hydrated (a Next page has React's markers on its DOM) and the network is quiet again before it measures or clicks. A page that never hydrates is measured as it is, and `runtime-errors` says why.
- **Redirects.** A route that ends on another path (a sign-in page, a locale prefix) is one `route-unreachable` finding for that route, naming the target; the other routes still run. Nothing is measured on the page it landed on.
- **Signed-in pages.** Add `"auth": { "storageState": "e2e/.auth/user.json" }` to `viewsonic-ui.config.json`: a Playwright storage state file (cookies and localStorage), relative to the project root. Every browser check and `shots` open their pages with it. Make one with `npx playwright codegen --save-storage=e2e/.auth/user.json <url>` after signing in. A missing file is a SKIPPED with that hint. Keep it out of git; it holds a live session.
- **Local apps only.** Every browser check and `shots` refuse a base that is not local (localhost, 127.0.0.1, [::1], `*.localhost`, `*.test`) unless `--allow-remote` is passed: the base usually comes from the repository's config, and the checks open it with the signed-in session and press keys and click (a maestro patch; upstream refuses only in `ux-flow`). Routes, from the config or `--route`, must be paths on that app (`/x`, never `@host/x` or `//host/x`). `shots` writes a `.gitignore` of `*` into its default folder, so screenshots of signed-in pages are never committed by accident (to commit baselines, pass `--out <dir>`), and refuses a committed link anywhere in that folder.
- **Inside the repository only** (a maestro patch). Every path the checks read stays inside the project's git repository (else the project folder): a `uiDir`, `sources`, `styles`, `componentCss` or `@import` that leads out, or a default folder committed as a link out, is refused by `run.mjs` and ignored, without a message, by the after-edit hook. The walks skip symbolic links, so a component, source file or page folder that is a link is not checked.
- **States.** `shots` takes query strings (`shots "/settings?state=empty"`): each query gets its own folder, `settings--state-empty`. Quote the route in a shell that treats `?` or `&` specially.
- **`full` and files.** `full` runs the static checks over the whole project unless the scope is narrowed with `--changed`; only the browser routes follow the changed pages.

## Component props: the after-edit hook and the lint rule

Not a `run.mjs` check, so nothing to run. The plugin's hook (`hooks/hooks.json`, `checks/eslint/on-edit.mjs`) runs after every Edit, Write or MultiEdit on a script file outside the ui folder and exits 2 with `file:line message` lines the agent sees at once: a variant value the component's `cva()` does not define (`Button has no size "md". Use one of: ...`), a prop name the component does not declare (`Button has no prop "colour". Did you mean "color"?`), a value outside a literal-union prop, and TypeScript's own errors on the JSX of a ui component (a missing required prop). The cva check needs no TypeScript; the rest needs the project's `typescript` (a project without it is told once). The type table is cached in the user's own cache folder (`$XDG_CACHE_HOME/maestro-uiux`, else `~/.cache/maestro-uiux`; a maestro patch, not the shared OS temp folder); an edit costs about 2 to 3 seconds. `install` can wire the same rule into the project's ESLint config as `viewsonic/valid-variant` (flat config only; an unrecognised shape gets printed instructions).

## Contrast fix loop

Level: `contrastLevel` in `viewsonic-ui.config.json`, `"AA"` (default, the floor: text 4.5, large 3, UI 3) or `"AAA"` (text 7, large 4.5, UI 3); both `contrast` and `contrast-rendered` judge against it and name it in every finding. Any BAD at the level means the design is not done. Pairs: the defaults in `checks/static/contrast.mjs` plus `contrastPairs` in `viewsonic-ui.config.json` (`{ "fg": "--x", "bg": "--y", "kind": "text" }`). Pairs are token NAMES; every value is read from the project's stylesheets, so the check holds no colours and works for any brand. Only light and dark are measured; a `data-*` scope other than `data-theme` is not a theme. Before using a new foreground on a surface, probe it: `node <skill>/checks/run.mjs contrast --fg --x --bg --y`.

1. Take the `try:` suggestions: existing tokens that pass on that surface in both themes, same role first.
2. Swap the use to the first one that keeps the meaning (a warning stays a warning). Re-run until GOOD.
3. Only when the output says `NO EXISTING TOKEN PASSES`, stop and ask the user: the pair, the ratio, what was tried, and the value that would pass. Add a token only after a yes. Never delete a pair to go green.
4. `unparseable colour` means the value is not hex, rgb(), hsl(), oklch() or color-mix(in srgb|oklab, …): write it in one of those so it can be measured.

A default pair whose tokens the project never declares is reported as SKIPPED, not BAD.

## What no check catches

Do these by hand (step 8, Review):

- A component redrawn from `<div>`/`<span>` with copied classes (only the selection control is guarded).
- An arbitrary class outside the system's names, `refs` only checks the system's families.
- Both themes looking right (judged in `shots`). Motion is sampled only for rows with a `specimen` (and `content-cut` only with a `swap.trigger`); the rest is judged by triggering the change and watching it. Contrast itself is measured (`contrast`, `contrast-rendered`), never judged by eye.
- Keyboard and screen reader beyond what `keyboard` drives: a clickable `div`, tab stops past the 200th, overlays beyond the 10th, whether a status change is announced, whether alt text and control names are useful, and phone width ([rules/accessibility.md](../rules/accessibility.md)).
- Whether copy is clear, kind and true, and whether one term is used for one concept beyond the verb pairs `term-drift` knows: `content` reads only written-out text; judged against [rules/content.md](../rules/content.md).
- The UX rules no check measures (1, 7, 9, 10, 12 to 15, 17 to 19), the placement half of 11, and whether a human message is a good one: answer the **Review** questions in [rules/ux.md](../rules/ux.md). `ux` cannot see an error that is passed through a variable or a prop before it is rendered, nor a handler written in another file; `ux-flow` cannot see a click that changes nothing the DOM shows (a canvas, a native validation bubble), and judges only what it clicks.
- Hierarchy, proximity, balance, white space and the rest of the seven foundations: judged from the screenshots against [rules/foundations.md](../rules/foundations.md).
- Patterns are never checked. No check fails because a screen does not follow a page pattern (`patterns/`); only the system rules are enforced.
- Adding a new token without asking, SKILL step 4, "Ask before adding a new value".
