# Bundling ViewSonic's UI/UX skill, and a design-system-aware Step 5 (v1.19.0, hardened in v1.20.0)

## Decision

Maestro bundles `elattar-uiux-design`, ViewSonic's UI/UX skill, as a second skill of the maestro plugin, and its Step 5 gate learns to defer to a project's own design system. Projects on the ViewSonic design system get the skill's design pass, rules and runnable checks inside maestro's flow; every other project gets a gate that no longer asks a token-driven system for a new palette or a Tailwind CDN mockup.

The owner asked for the skill to be copied in (not referenced) and bundled inside maestro (not shipped as a second marketplace plugin), and confirmed that the content may be published in this public repository.

## What changed against upstream

Every vendored file is byte-identical to upstream except these. Re-apply all of them on every sync.

1. **`SKILL.md` description narrowed.** Upstream's description fires on any UI task "in any project, even if the user never mentions design or the design system". Bundled into maestro, that would load ViewSonic's tokens and rules into every maestro user's UI work on other systems. The description now scopes the skill to projects on the ViewSonic system (a `viewsonic-ui.config.json` or `.viewsonic-ui/` folder, or the foundation's `--color-action-*` and `--color-value-*` tokens) or an explicit request. The body is untouched.
2. **`checks/install.mjs` refuses to write through a symbolic link.** Upstream's installer refreshes `.viewsonic-ui/checks/` by copying its files in and deleting every other file there, and writes the hook, workflow, config, `.gitattributes` and ESLint config with plain writes. A repository that commits any of those paths as a link to a folder outside the project would have the installer overwrite files there and delete the rest. The patch (`linkOnPath`, `linkUnder`) checks every target path component and every entry under the vendored folder before planning or writing, and refuses with exit 1 and a message naming the link; a dangling link is refused too, and so is a path it cannot inspect (any error other than "does not exist"), so nothing is written blind. The dry run refuses as well. It is a hard stop: a monorepo package whose `eslint.config.*` is a link to a shared config is refused, and the user wires the ESLint rule by hand.
3. **`checks/test/plugin-shape.test.mjs` adapted to maestro's layout.** Upstream asserts its own plugin shape. The adapted test keeps every assertion and points it at the bundle: plugin `maestro`, marketplace at the plugin root with source `./`, commands `uiux-*.md`, and a `PostToolUse` entry whose wrapper assigns `CHECK=` to the vendored `on-edit.mjs`.
4. **`checks/eslint/on-edit.mjs` loads the project's `typescript` only at `MAESTRO_UIUX_HOOK=full`.** Upstream resolves the edited project's own `typescript` package on every run, before any other gate, so any repository with a `package.json` and a planted `node_modules/typescript` runs its code on an agent edit. At `MAESTRO_UIUX_HOOK=on` the patched check keeps to its existing cva-only path, which reads files and runs nothing from the project, and skips upstream's "this project has no typescript" notice; `full` restores upstream's behaviour, and so does an unset variable, so upstream's own tests (which run the module directly) are unaffected.
5. **`checks/test/eslint-variants.test.mjs` finds `typescript` by walking up.** Upstream looks six folders above the test, which is its own repo root only in its `plugins/<name>/skills/<name>/` layout; in maestro's layout the "prop names and union values" suite silently skipped. The patch walks up, as the same file's ESLint lookup already does.
6. **Hardening (v1.20.0): the review findings v1.19.0 had deferred to upstream, and those the v1.20.0 review found, fixed here.** Each of the eleven touched upstream files carries a `maestro patch (not upstream)` comment at the change; the shared helpers are in the added `checks/maestro-guards.mjs`.
   - **Paths stay inside the repository** (`variants.mjs`, `props.mjs`, `config.mjs`, `lib.mjs`). The boundary is the project's git repository (the nearest folder holding `.git`, searched no higher than just below the home folder, so a home kept in git never counts), else the project folder, so a monorepo's shared ui package still counts. A `uiDir`, `sources`, `styles`, `componentCss` or `components.json` alias that leads out of it (`../outside`, or a link out, a dangling one included) is ignored by the hook and refused by `loadConfig`, and so is a default folder (`app`, `components/ui`) committed as a link out; an `@import` that leads out is not read. A config may not set `root` or a prototype key. The ui-folder walk, the static checks' walk and the route walk skip every link (upstream followed them, and threw on a dangling one or a loop, which switched the hook off or stopped the run); the ui walk also leaves out files over 1 MiB and stops at 2,000 files, 32 MiB or 50,000 entries. The config and `components.json` are read only from inside the repository (never through a link out) and, like every stylesheet the config collects or names, only as a regular file of bounded size (a FIFO hung the run); block comments are stripped in one pass (the lazy pattern was quadratic on an unterminated one).
   - **A bounded after-edit check** (`eslint/on-edit.mjs`, `variants.mjs`, `props.mjs`). The check runs in a child process killed after 20 s (below the hook's 30 s timeout), which turns any slow path into a silent exit 0. The scan for `cva(` calls was quadratic on a crafted file twice over (an unbounded pattern, about a minute for 1 MiB, and a rescan to the end of the file for every unclosed call), and so was the line count of each tag; each now reads every character once. The child is marked on its command line, which a project cannot set, and when it is stopped the agent is told once per project that its edits are not being checked. An edited file over 1 MiB is skipped. Each message clips the value (80 characters) and the list of allowed values (20 entries of 40), at most 50 findings are printed with a count of the rest, and the child's output is capped at 256 KiB.
   - **No writes in the shared temp folder** (`props.mjs`, `eslint/on-edit.mjs`). The prop-table cache and the "no typescript" marker live in `$XDG_CACHE_HOME/maestro-uiux`, else `~/.cache/maestro-uiux`, else `maestro-uiux-<uid>` in the OS temp folder, each used only if it is a real folder this user owns (then tightened to 0700). The cache is written to a new file and renamed into place; the marker is created exclusively; with no usable folder the notice is not shown, rather than shown on every edit.
   - **One finding, one line** (`eslint/on-edit.mjs`, `run.mjs`). Control and format characters (bidi and zero-width marks, tag characters, the BOM), line separators, variation selectors and the invisible Hangul fillers in a finding become a space, so a variant value or file name with a line break cannot forge a second line of hook feedback, a `GOOD` line in `run.mjs` output or a line of the installer's plan, and cannot hide text. Other Unicode, such as `app/café.tsx`, is kept (maestro's wrapper narrows the hook's output to ASCII on its own). The `node_modules` skip splits on both separators (upstream's pattern matched only `/`).
   - **Strings from the repository are validated where they reach a URL, a shell line or a workflow** (`maestro-guards.mjs`, `config.mjs`, `run.mjs`, `install.mjs`). `baseUrl` must be an http or https URL with no credentials, no line break, control or invisible character and no `${{`, so it can neither end the workflow's `run: |` block nor open a GitHub expression (a quote or space stays safe inside upstream's single quotes, as its own test expects). Routes (from the config, `--route` or the command line) and motion specimens must start with a single `/` and hold no space, backslash, control or invisible character, so `base + route` stays on the base's origin; an empty specimen still means none. The installer refuses a project folder name below the git top level that holds anything but letters and digits (any script) and `. _ @ + -`, which would otherwise run inside the generated pre-commit hook; the generated workflow gains `permissions: contents: read`; and the dry run names the workflow's real path at the git top level.
   - **Browser checks run against a local app only** (`browser/lib.mjs`, `browser/ux.mjs`, `browser/shots.mjs`). Upstream refused a base that is not local only in `ux-flow`; every browser check and `shots` now refuse it unless `--allow-remote` is passed, before anything is fetched or launched, because the base usually comes from the repository and the checks open it with the signed-in session and press keys and click. The reachability probe no longer follows a redirect. `shots` refuses a committed link at its default folder, at any route folder or at any file inside one, and a route whose folder would be `.`, `..` or the `.gitignore`; it takes each screenshot as bytes and writes it by rename, and reports a folder in a file's way for that route instead of stopping; and once the browser is up it writes a `.gitignore` of `*` into its default folder (a committed one must hold just `*`), so screenshots of signed-in pages are never committed by accident.
   - **The installer's residual paths** (`install.mjs`). The guard now runs before the config, the ESLint file or either `package.json` is read, and refuses a path part that is not a folder (`.viewsonic-ui` as a plain file ended in a stack trace) and a target that is not a regular file (a FIFO hung the dry run). The home folder itself (or above it), a folder inside `.git` and a folder outside a git work tree are refused (from inside `.git`, `core.hooksPath` would have pointed git at the repository's own committed hook). A project folder reached through a link that sits inside a repository and leads out of it, to a plain folder or to another repository, is refused, whether named by `--cwd` (relative or absolute) or by the shell's `$PWD` (`process.cwd()` resolves links, so the shell's name for the folder is used when it resolves to the same place); a link above every repository (macOS `/tmp`, a linked projects folder) is not judged. Every write is a new file renamed into place (the config skeleton an exclusive create), so a link or hard link at a target, or one swapped in after the check, loses only its name and the file it shared is never written; an existing file keeps its mode, and a read-only target is refused before anything is written, as a plain write would have failed (the vendored copies, which are maestro's, are refreshed either way).
   - **`checks/map.md`** says where the cache lives, that browser checks need a local app or `--allow-remote`, that walks skip links, that a ui folder outside the repository is ignored without a message, and that `--out` opts out of the self-ignoring screenshot folder.
7. **Added:** `LICENSE` beside the skill, so the MIT notice travels with every copy; `checks/maestro-guards.mjs`, the helpers patch 6 uses; and `checks/test/maestro-patches.test.mjs`, `maestro-hardening.test.mjs` and `maestro-hardening-io.test.mjs`, with their shared `maestro-helpers.mjs`, the tests for patches 1, 2, 4 and 6 and the command edit below.

Outside the skill folder:

- **Commands** `commands/uiux-{setup,check,check-full,review}.md` are upstream's four commands, renamed so they read as `/maestro:uiux-check` rather than an ambiguous `/maestro:check`. Their bodies are upstream's, except that the `allowed-tools: Bash(node:*), Read` line is removed. `Bash(node:*)` pre-approves any `node` command (`node -e ...` included) while a command is active, and for `uiux-setup` it would have made the model's reading of "only after the user says yes" the only gate before `install --yes`; an unscoped `Read` pre-approves reading any file. Without the line, every run goes through the user's normal permission prompt. `uiux-check` and `uiux-check-full` load the project's own `typescript`, and `uiux-check-full` and `uiux-review` its Playwright, so they run repository code as its own test suite would (user-invoked, behind the permission prompt); `uiux-setup` only checks that Playwright resolves.
- **Hook** `hooks/uiux-on-edit.sh` is new and **opt-in**, at two levels: `MAESTRO_UIUX_HOOK=on` (variant values, no project code, through patch 4) and `full` (upstream's full check, which loads the project's `typescript`). Upstream's hook runs `node .../on-edit.mjs` after every edit for people who chose that plugin. That check loads the edited project's own `typescript` package before any other gate, so in a cloned repository with a planted `node_modules/typescript` it runs that repository's code after an agent edit, with no install or build by the user; and once bundled it would do so for every maestro user. Off by default, the user turns it on knowingly, in their own environment, and `full` only for repositories they trust. The switch is global, so `full` cannot be limited to some repositories. When on, the wrapper stays silent without Node or the script, passes the check's exit 2 through, and turns any other exit into a silent 0 (upstream's own contract for internal errors). The check's findings quote names from the project's files, so the wrapper prefixes them with a line labelling them as project data, keeps only printable ASCII (under the C locale, so control characters and invisible or bidirectional Unicode go in any user locale; upstream's own messages are ASCII), caps each line at 300 characters and keeps the first 20 lines, all with shell builtins. It looks at no more than 64 KiB of the check's output and cuts each line before stripping it, because a pattern replace over one huge hostile line stalls bash into the hook's 30 s timeout, and it discards bash's own warnings so a NUL byte cannot leak one (with the plugin's path) ahead of the header. Upstream's trailing "Fix these now" line still arrives; the header frames it and every finding as project data, accepted at an opt-in level the user chose. Since patch 6 the check prints each finding as one line, so a crafted name with an embedded newline can no longer forge extra lines. The variable belongs in the user's shell profile or user settings. A project's own `.claude/settings.json` could set it too, but a project trusted to do that can already run hooks of its own, so it gains nothing it did not have.
- **Vendored text that assumes the hook is on.** Three upstream sentences describe the after-edit check as always running: `SKILL.md` step 7 ("flagged automatically after every edit"), `checks/map.md` ("Component props: the after-edit hook and the lint rule") and `system/components.md` ("the after-edit hook rejects a variant it does not define"). They hold only when the user has turned the hook on. They are left as upstream wrote them; `frontend-design-trigger.md` tells maestro what to run instead when the hook is off (the project's lint rule and type check), and never to report variant or prop validity from `run.mjs fast`, which does not check them.

## The Step 5 changes

`frontend-design-trigger.md` gains a "Design-system projects" section, read before the substeps. A project counts only when it has its own tokens in the repo and something enforces them; stock shadcn/ui, Tailwind defaults, Material or Bootstrap as shipped do not count, and when unsure the project is treated as having no system. Then:

- 5a picks composition, never vocabulary: palette, type roles, radius, spacing, shadows and motion come from the system's tokens, and 5a's style list, palette, typography-pairing and motion lines apply only to projects without a system.
- Every voice (5d UI UX Pro Max, Taste, Transitions) stays inside the system; a suggested new token or font pairing is an ask, not a refinement.
- A missing value is an ask, naming the closest token, never an arbitrary literal.
- 5b becomes a local preview route on the system's real components, gitignored, for new surfaces, redesigns and style refreshes.
- The anti-template ban reads against composition: using the system's restyled components is required, not a template smell.
- Both themes belong to the system: a colour that needs a `dark:` variant means a token is missing.

On the ViewSonic system it routes 5a, 5e, 7 and 8 to the bundled skill's steps while maestro's gates (5c approval, TDD, Step 6, the Evidence Gate, 8.5) keep their authority.

`uiux-checklist.md` drops two items that contradicted token-driven systems (stock Tailwind palette as "tokens", `dark:` variants as the default) and adopts upstream's transferable rules: new values are asked for, a description is set smaller than its title, contrast is measured in both themes (disabled controls exempt but distinct), skeletons match the footprint and swap once, every action gives two signals, and a closing group that runs at Step 8, not 5e (a green build is the floor; both themes seen in a browser; report what was verified, never a skipped check as passing).

`SKILL.md` is unchanged: the hot path had 138 bytes of budget left, and Step 5 already reads `frontend-design-trigger.md` first.

## Alternatives considered

| Option | Why it lost |
| --- | --- |
| Reference only: route to the plugin in ViewSonic's private marketplace | The owner asked for a copy. It would also leave every non-ViewSonic maestro user without the runnable checks, and a private marketplace cannot be installed from outside the organisation |
| Rewrite the rules in maestro's own words | Loses the checks and their 1,100-test suite, and drifts from upstream the day it lands |
| Ship it as a second plugin in the `impravin22` marketplace | Recommended at planning (its hook and description would reach only people who install it), but the owner chose one install. The narrowed description and the opt-in hook are the mitigation |
| Keep the hook on by default, gated on a ViewSonic marker in the wrapper | Still runs a repository's own `typescript` on every edit in any repository that carries the marker, which the repository itself controls |
| Keep upstream's directory layout through a custom skills path in `plugin.json` | Would avoid adapting the plugin-shape test, but rests on harness behaviour this change did not verify |

## Security review

**Before vendoring.** SkillSpector scanned the upstream plugin statically (its LLM pass did not run) and reported risk 81, CRITICAL, `DO_NOT_INSTALL`: 3 HIGH and 29 MEDIUM. All were false positives on reading: a `process.env` spread in a temp-repo git test, the word "override" in a comment about CSS `!important`, the plain `"description"` key in upstream's `plugin.json` (not vendored), rules and evals that tell the agent *not* to act without asking, and the project-scoped loading of Playwright and TypeScript. A rescan of the bundled tree reports three HIGH, all false positive: the same two, and the same `process.env` pattern in maestro's own `checks/test/maestro-patches.test.mjs`. The v1.20.0 rescan reports four HIGH, all false positive: those three and the same pattern in `checks/test/maestro-hardening.test.mjs`, whose refused sample inputs are deliberately inert (`echo injected-step`, not a download-and-run line) so the scan does not read them as payloads.

## Tests

- **The vendored suite runs in CI** (`uiux` job, Node 22 and 24), with upstream's own TypeScript 5.9.3 and ESLint 9.39.5 installed at the repo root (exact versions, no lockfile, no install scripts), so the ESLint rule `/maestro:uiux-setup` wires is exercised too. In the bundle it reports 1,213 tests: 1,123 pass, 0 fail, 90 skipped, every skip a browser check that needs Playwright. The job fails if fewer than 1,000 tests pass (a moved folder or a bad sync would otherwise run nothing and stay green) or if anything other than a browser check skips.
- **Three skip patterns**, each an exact name, cover tests that need upstream's own tree: the suite `patterns: skeleton code passes the static checks` (copies upstream's styles and checks snippets against its components), the test `an unknown prop name gets a nearest-name suggestion` (needs upstream's React types), and the test `probe with only --fg is a usage error` (needs a shadcn project as the working directory). Upstream's CI runs them.
- **`checks/test/maestro-patches.test.mjs`** proves, for patch 4, that at `on` a planted `typescript` never loads while the cva check still flags the variant, and that `full` and an unset variable load it as upstream does; (and that any other value, `ON` or an empty string among them, fails safe); for patch 2, that the installer refuses a linked `.viewsonic-ui/checks`, a linked `.viewsonic-ui` in the dry run, a folder or a file link inside the vendored folder, linked hook, workflow, config and `.gitattributes` targets, a linked `.github` at a monorepo's git top level, a linked `eslint.config.mjs`, a dangling link and a folder it cannot read, comparing a snapshot of the whole outside folder before and after each case, and still installs a clean project; and for patch 1 and the commands, that the narrowed description and the missing `allowed-tools` line survive a sync.
- **`checks/test/maestro-hardening.test.mjs` and `maestro-hardening-io.test.mjs`** (57 tests, sharing `maestro-helpers.mjs`) build a hostile repository for each patch 6 fix and prove it holds, comparing a snapshot of an outside folder before and after where a write could escape. Among them: a `uiDir`, alias, default folder or link out ignored or refused, while a monorepo's shared ui folder is kept; a home kept in git not taken as the boundary; dangling links and loops no longer stopping a walk; the walk's link skip and every cap; the cache and marker in a private folder, a planted link replaced, and the temp-folder fallback; a newline in a value staying on one line and a non-ASCII path kept; output clipped to 50 findings; the deadline killing the check silently; the crafted file that made the cva pattern quadratic finishing at once; `root`, `__proto__`, `baseUrl`, routes, specimens, `sources`, `styles`, `componentCss` and `@import` validated; a FIFO config refused at once; a file name unable to forge `run.mjs` output; a non-local base refused before anything runs; the probe not following a redirect; `shots` writing by rename, ignoring itself and refusing a link at any level and a `..` route; and the installer refusing a hostile base URL or folder name, a project folder linked out of its repository (by `--cwd`, relative `--cwd`, `$PWD`, or to another repository), `.viewsonic-ui` as a file and a FIFO config or `package.json`, while a hard-linked `.gitattributes` leaves the file it shared untouched. A stub Playwright planted in the test project lets the screenshot writes run without a browser. Against v1.19.0's checks with `maestro-guards.mjs` added (without it every test fails at import), 43 of the 57 fail; the other fourteen test the new helpers directly or are controls that hold either way. Every hook run in them, and the suite in CI and in CONTRIBUTING, uses a scratch cache folder, so no run writes the real `~/.cache`.

## Syncing from upstream

Upstream is private, so `track-upstream.yml` cannot watch it from public CI. To sync by hand, from a machine with access:


## Known limits

- The skill's description (548 characters) joins every maestro session's skill listing, ViewSonic project or not. That is the cost of bundling over a separate plugin.
- The copy goes stale between syncs, and nothing public can detect it.
- The after-edit hook is off unless the user turns it on. With it off, no `run.mjs` check sees invalid props or variants; they surface only through the project's lint rule (`viewsonic/valid-variant`, which `/maestro:uiux-setup` wires) and its type check. At `on`, only variant values are checked as edits land.
- Roughly a dozen upstream tests that need upstream's own tree do not run here.
- Patch 6 is wide: eleven upstream files carry a change. Each sync re-applies it by hand, and the hardening tests fail until it is.
- Every browser check now needs `--allow-remote` for a base that is not local (upstream asked only in `ux-flow`). Running against a staging URL takes the flag.
- The walks skip links: a ui component, source file or page folder that is a link, even one that stays inside the repository, is not checked.
- The installer refuses a monorepo folder with a space in its name, or one that starts with `@`, `+` or `-`; wire the hook and workflow by hand there.
- A check stopped at the 20 s deadline (a cold TypeScript pass at `full` on a very large ui folder, say) checks nothing, on every edit, until the cause is gone; the agent is told once per project.
- When the repository's top level is the home folder (some containers set `HOME=/workspace`), the home stop leaves the project folder as the boundary, so a `uiDir` in a sibling package is refused.
- The installer sees a link on the way to the project folder only through `--cwd` or the shell's `$PWD`; started with a physical working folder and no `$PWD`, it cannot tell, and the plan's `note` line shows the real folder instead.
- What patch 6 leaves open: a same-user process that swaps a folder above an install target for a link between the check and the write (it already runs as the user); a project folder reached through a link in a folder that is in no repository (an unpacked archive with a link inside) is not judged, since nothing says where it may lead; `auth.storageState` may still name a file anywhere (Playwright reads it and its cookies stay bound to their domains); Playwright's own navigation still follows a redirect from the local app; the generated workflow's actions are pinned to tags, not commits; and an `@import` outside the repository is dropped without a message.
